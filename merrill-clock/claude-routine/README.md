# Claude Remote Routine 設定

## 這個排程做什麼

每個美股交易日，在美國開盤前：

1. 讀取 Google 文件「**美林時鐘 每日摘要**」（由 Apps Script 每日更新，含機器可讀 JSON）
2. 做**選擇性**的關鍵判讀（v2）：先算「今天變了什麼、為何是今天」，只保留過門檻的 2–4 個指標，
   再補上質性脈絡（驅動來源、歷史 base-rate、政策路徑、總經 vs 市場落差）與三情境機率
3. 依警示等級（🔴／🟡／⚪）寄出 Email；沒有新資訊的日子就是⚪五行短信

**排除方式**：把 `list_triggers` 的輸出當 JSON 解析、直接取該 trigger 的
`derived_state.prompt`。（先前用字串搜尋往後找 `"prompt":"` 的做法會跨到別的 trigger，
結論不可信——不要再用那個方法。）

**修復**：以 `update_trigger` 寫入 `ROUTINE_PROMPT.md` 的內容，並獨立回讀確認
`derived_state.prompt` 與實際觸發用的 `session_request.events[0]` 兩處都已更新。
被覆蓋的舊文字存於 `_backup/overwritten-tw-wrap-prompt-20260903.md`。

正常的台股 Wrap 是另一支 `tw-aftermarket-wrap`（cron `15 7 * * 1-5` ＝台北 15:15，

## 改版記錄

### v3 — 有變動／無變動的日子要長得不一樣

v2 仍有兩個漏洞：

1. **狀態被當成事件**。「整體 vs 核心差距 > 0.75σ」「距翻面 < 0.35σ」都是狀態，
   一旦成立會持續數週，等於天天觸發 🟡——這跟當初 Apps Script「VIX≥30 天天發信」是同一個病。
   v3 全部改成邊緣觸發：**只認「今天跨越」，不認「已經在線的另一邊很久了」**。
2. **模型不記得昨天寫過什麼**。每次觸發都是全新 session，所以「不要重複昨天」這條規則
   在 v2 其實無法執行。v3 新增**步驟 1.5：用 Gmail 搜尋 `in:sent subject:"美林時鐘"`
   讀回自己上一封信**，用途有三：算相對增量、對前一次判斷問責（錯了要明寫修正，不默改）、防重複。

並把兩種日子改成**兩種文體**，而不是同一份報告的長短版：

| | ⚪ 維持日 | 🟡／🔴 事件日 |
|---|---|---|
| 回答的問題 | 「還在等，等什麼」 | 「變了，所以呢」 |
| 文體 | 純文字四行 | 分節報告＋散文推論 |
| 表格 | 一個都不准有 | 三情境表＋附錄表 |
| 質性脈絡／三情境／上網搜尋 | 全部跳過（步驟 3–5 不執行） | 必做 |

⚪ 日的四行是固定骨架：維持什麼／日頻三個數字／最近一條線還差多遠／在等什麼。
沒有新輸入就不會有新結論，重跑一次分析只會產生換句話說的假新意。

### v2 — 從數據報表改成關鍵判讀（2026-09-01）

第一次實際運行的信把 40 個欄位逐一列出並解釋定義，收信人得自己從中挑重點——資訊密度太低。
v2 針對這點重寫，並參考 `us-session-logic` skill 的研究方法（只取精神、不抄格式）：

| 改動 | 解決什麼 |
|---|---|
| **思考／交付分離鐵則** | 禁止「一致性：背離」「訊號強度：偏弱」這類貼方法標籤的句子；每句都必須是結論而非流程 |
| **重要性門檻表** | 沒過門檻的指標完全不寫。舊版連「未達 0.75σ 不算顯著」都要佔一列 |
| **「為何是今天」檢驗** | 總經座標是月頻的，一個月才動一次。逼模型分辨新增量／存量結算／機械效應，避免每天重複同一句話 |
| **歷史 base-rate 校準** | 用 `月度軌跡`＋`近期轉折事件` 算「這象限平均撐幾版」「暫定轉確認的命中率」，取代憑印象的「通常會…」 |
| **借來的結論一律重推** | `建議資產` 是機械輸出。要求先判斷通膨是需求拉動還是成本推動（假過熱），再說框架建議成不成立 |
| **三情境機率化** | 機率合計 100%、不三等分、各配可觀察檢驗條件，並點出最脆弱的前提 |
| **落差機會四件事** | 總經 vs 市場的背離要寫齊：落差在哪／誰承載／何時裁決／錯了怎麼知道 |
| **反直覺錨＋反事實＋機制連續** | 因果不能跳環；每封信至少一個與直覺相反的觀察 |
| **印前自檢 12 條** | 含逐句刪除測試：刪掉後結論不變的句子一律刪 |

## 前置條件與上線順序

1. Apps Script 端完成部署（`setup_StoreSecrets()` → `refresh_Calibration()` → `backfill_History(3)`）
2. 執行 `run_ExportDigest()`，確認雲端硬碟出現「美林時鐘 每日摘要」文件
3. 在 Routines 介面為排程掛上 Google Drive 與 Gmail
4. Apps Script 每日觸發器設在台北上午 6–7 點

順序反了也不會壞：排程會在步驟 0／步驟 1 偵測到並回報缺什麼。

## 排程時間：為什麼是台北早上、而且是週二～週六

### FRED 這七條序列全都是盤後資料

| 序列 | 內容 | 可取得時間 |
|---|---|---|
| `VIXCLS` | VIX 收盤價 | 美東收盤後當晚 |
| `T10Y2Y` | 10Y−2Y（來自 H.15 殖利率曲線） | 美東傍晚（財政部公布後） |
| `BAMLH0A0HYM2` | ICE BofA 高收益債 OAS | 隔夜／隔日美東早上 |
| `DFF` | 有效聯邦基金利率 | 隔日美東早上發布**前一營業日**的值 |
| `CFNAIMA3`／`CPIAUCSL`／`CPILFESL` | 月頻 | 發布日美東 08:30 |

**沒有盤前更新這回事。** 所以要「確保當日資料發布完成」，正確的時點是美東傍晚之後——
換算成台北就是隔天早上 6 點之後。

### 星期對齊：是週二～週六，不是週一～週五

Apps Script 的週末防線是用**美東**星期判斷的（`Utilities.formatDate(new Date(),'America/New_York','u')`）。
台北早上 07:00 = 美東前一天 19:00，所以：

| 台北 | 美東 | 結果 |
|---|---|---|
| 週二～週六 07:00 | 週一～週五 19:00 | ✅ 執行，處理前一交易日收盤 |
| 週日 07:00 | 週六 19:00 | 自動略過（無新資料） |
| 週一 07:00 | 週日 19:00 | 自動略過（週五收盤已在週六處理完） |

若 Claude 排程照直覺設成「週一～週五」，會在**台北週一空跑**（Apps Script 已略過、資料是舊的），
而且**漏掉台北週六**——也就是漏掉整個週五收盤的判讀。

### 實際設定

| 環節 | 時間 | 說明 |
|---|---|---|
| Apps Script 每日觸發器 | 台北 **上午 6–7 點**（設每日即可） | 週日／週一會自己略過 |
| Claude Routine | 台北 **週二～週六 08:23**（UTC cron `23 0 * * 2-6`） | 留給 Apps Script 約 80 分鐘餘裕 |

> **上線後第一週要驗一件事**：高收益債 OAS（`BAMLH0A0HYM2`）是 ICE 授權資料，
> FRED 的更新時點比其他幾條晚。若你發現試算表的「高收益債利差」在台北早上跑的那一列
> 經常比 VIX 落後一天，把 Apps Script 觸發器改到台北晚上 9–10 點（＝美東早上 9–10 點）即可補上；
> 這時 Claude 排程要跟著改成台北週二～週六的更晚時段，或直接改成美股盤前時段。
> 程式本身對此是安全的——它一律取「最新可得」的值，不會因為某條序列落後就整列失敗。

## 與 Apps Script 的信件如何分工

- **Apps Script**：只在偵測到轉折或跨越警示門檻時，寄一封快速的「事件通知」（純數據、無 AI）。
- **Claude routine**：每個交易日寄一封深度分析信，等級 ⚪ 時會刻意寫得很短。

兩者不重複：Apps Script 那封是「發生了什麼」，Claude 這封是「所以呢」。
若覺得太多，把指令碼屬性 `ALERT_EMAIL` 留空即可停掉 Apps Script 端的信。
